# InkTalk 每日候选热词与纠错证据方案

## 结论

方案包含三条独立路径，三者不能混为一谈：

- 用户可以从任意一条每日原始记录中手动选择词语或单字，并直接加入热词。这是用户明确确认的热词，可信度最高，也不依赖 AI。
- 当日原始输入已经保存在 `input_entries`，可以自动提取高频词、专有名词、缩写、英文名称和重复短语，但这些内容只能作为待确认候选。
- 输入法需要新增删除与后续输入事件记录，用于形成「删除片段 → 新输入片段」的可能纠错。当前记录没有这些字段，因此新版本上线前不能回溯历史纠错。

推荐先交付「手动逐字选择 → 确认 → 加入热词」闭环，同时建设编辑事件记录。自动提取可以随后接入同一审核界面。任何自动候选或可能纠错都不得自动进入 ASR 热词列表。

## 当前数据边界

### 已有数据

`InputHistoryStore` 当前保存：

- `created_at`：写入时间；
- `source`：语音、手写、数字键盘、指令或 AI 处理；
- `content`：本次提交的文本。

每日整理会把所选日期的原始记录发送给当前 AI 服务，并把整理结果单独写入 `daily_organizations`。原始记录保持只追加，不被整理结果覆盖。

### 当前没有的数据

- 删除了什么文本；
- 修改前和修改后的词；
- 修改发生在哪个光标位置或选区；
- 修改是否由用户、宿主 App、其他键盘或 AI 完成；
- 多次删除与后续输入是否属于同一次纠错。

Android `InputMethodService` 可以在当前输入法活跃时读取光标附近文本和选区变化，也可以通过 `GET_EXTRACTED_TEXT_MONITOR` 请求编辑器回传文本更新。但是，编辑器可以不满足完整文本请求，调用可能返回 `null`，返回文本也可能少于请求长度；`onUpdateSelection` 本身只报告新旧选区位置。输入法被切换或关闭后，InkTalk 不能继续观察宿主编辑。因此，宿主文本差异只能作为机会性证据，不能作为跨 App、跨键盘都可靠的纠错事实。

## 推荐产品方案

### 第一阶段：从每日记录手动选择热词

每条原始输入记录增加「选择热词」操作。点击后，记录在当前卡片内展开为可选择单元，用户逐步点选需要加入热词的词语或单字。

#### 选择单位

- 中文按用户可见字符展开。
- 英文、数字、组合附加符号和 emoji 按 Unicode 字素簇处理，不按 UTF-16 code unit 拆分，避免截断代理对或组合字符。
- 点击单个单元可选中或取消，可逐步组成连续或非连续选区。
- 相邻选中单元合并为一个热词；不相邻选区形成多个独立热词，不跨空白自动拼接。
- 空格和标点默认作为边界，但允许用户主动包含 `-`、`.`、`+`、`/` 等连接符，以支持 `GPT-5`、版本号和复合名称。

#### 交互流程

1. 点击某条记录的「选择热词」。
2. 记录正文切换为逐字选择状态，原始记录本身不发生修改。
3. 用户点选一个或多个连续片段。
4. 页面实时展示待加入热词，例如「InkTalk」「百炼」「GPT-5」。
5. 点击「加入 3 个热词」后，再执行大小写不敏感去重和长度校验。
6. 成功项立即进入用户热词；重复、无效或超长项分别提示原因。

界面需要提供「取消选择」「清除所选」和「加入热词」操作。已经存在于热词列表的完整片段应显示「已在热词中」，避免重复添加。屏幕旋转或 Activity 重建时应恢复当前记录、选区和待加入列表。

这条路径不需要 AI 配置，也不要求用户先执行「整理当日内容」。敏感输入框原本不进入每日记录，因此不会出现在选择界面。

### 第二阶段：自动提取每日候选热词

在「当日整理」结果下增加「今日候选热词」卡片。候选来源包括：

- 当天重复出现的词或短语；
- 产品名、人名、地名、机构名；
- 英文名称、缩写、大小写敏感词；
- 中英混合词、带数字的型号或版本名；
- 当前热词列表中尚不存在的领域词。

每个候选至少展示：

- 词语；
- 候选原因，例如「今日出现 3 次」或「可能为专有名词」；
- 来源类型，例如「输入内容」或「可能的纠错」；
- 「加入热词」和「忽略」操作。

产品规则：

1. 只展示候选，不自动添加。
2. 已存在于当前热词或内置词表的内容不再推荐。
3. 忽略状态需要持久化，避免同一候选每天重复出现。
4. 加入时保留用户现有热词，不恢复用户主动清空的默认词表。
5. 候选包含敏感或过长内容时丢弃，不进入界面。

### 第三阶段：记录删除与变更，生成可能的纠错

在 InkTalk 输入法活跃期间记录结构化编辑事件：

- 删除前读取选中文本或光标前的有限文本。
- 单次删除和长按连续删除都记录；连续删除合并为一次删除批次，不为每个字符生成一条候选。
- 删除后重新读取光标附近文本；只有能够验证文本确实变化时，才把事件标为 `confirmed-delete`。无法验证时保存为 `unverified-delete`，不参与自动纠错推荐。
- 记录随后通过语音、手写或数字键盘成功提交的新文本，以及提交来源和编辑会话。
- 在同一编辑会话、相邻光标范围和可测试的短时间窗口内，把「删除片段 → 新输入片段」组合为可能的纠错。
- 使用本地字符或词语差异算法缩小改动范围，例如从整句提交中提取真正变化的片段，不把整段语音都当成新热词。

该证据只能标记为「可能的纠错」，除非用户在界面中确认。以下情况不应生成纠错候选：

- 仅移动光标或选择文本；
- 删除整段内容但没有紧邻的新输入；
- AI 指令、总结、翻译或整理造成的大段替换；
- 输入法已切换或宿主编辑器上下文不完整；
- 密码、PIN 等敏感输入框。

纠错候选与自动提取候选进入同一个「待确认候选」区域，展示「原词 → 新词」和证据来源。用户可以选择「加入新词」「忽略」或「这不是纠错」。删除事件和原始输入记录分别保存，不用纠错结果覆盖历史内容。

对于 `GET_EXTRACTED_TEXT_MONITOR` 观察到、但并非 InkTalk 主动发起的宿主文本变化，只保存为低置信度诊断数据；在真实宿主兼容性和误判率得到验证前，不向用户生成纠错候选。

不建议通过无障碍服务监控其他 App 的完整编辑过程。该方案权限过重、隐私风险高，也会偏离输入法的合理职责边界。

## 数据设计建议

原始输入表继续保持只追加。新增热词选择、候选和编辑事件表，不把新字段堆叠到 `input_entries`。

### 手动选择记录

| 字段 | 用途 |
| --- | --- |
| `source_entry_id` | 对应的原始输入记录 |
| `term` | 用户确认的热词 |
| `start_offset` / `end_offset` | 在原始记录中的字素簇范围 |
| `created_at` | 确认时间 |

该表用于追溯热词来源，不改变 `input_entries.content`。

### 候选热词

| 字段 | 用途 |
| --- | --- |
| `local_date` | 候选所属日期 |
| `term` | 候选词语 |
| `normalized_term` | 大小写不敏感去重键 |
| `source_kind` | `manual-selection`、`daily-input` 或 `possible-correction` |
| `source_entry_id` | 可选的原始记录 ID |
| `edit_event_id` | 可选的纠错事件 ID |
| `evidence_count` | 出现次数或证据数量 |
| `reason` | 面向用户的简短原因 |
| `status` | `pending`、`added`、`dismissed` |
| `source_max_entry_id` | 对应的原始记录上界 |
| `created_at` | 生成时间 |

候选与每日整理结果分别保存。重新整理当天内容时，可以针对新增的原始记录增量刷新候选，但不得覆盖已经确认或忽略的状态。

### 编辑事件

| 字段 | 用途 |
| --- | --- |
| `editor_session_id` | InkTalk 内部编辑会话标识，不持久化宿主全文 |
| `event_type` | `delete`、`commit` 或 `replacement-candidate` |
| `verification_state` | `confirmed` 或 `unverified` |
| `deleted_text` | 已验证删除的有限片段 |
| `inserted_text` | 随后成功提交的文本 |
| `input_source` | 语音、手写或数字键盘 |
| `cursor_before` / `cursor_after` | 编辑器提供可靠绝对位置时才保存 |
| `created_at` | 事件时间 |

编辑事件不得保存宿主包名、完整文本或稳定设备标识。若位置不是可靠绝对偏移，应明确标记未知，不能自行推算。

## 热词管理集成

热词编辑页分为两部分：当前热词编辑器，以及独立的「待确认候选」区域。自动候选和可能纠错不能直接混入文本编辑框；从每日记录手动选择并确认的热词可以立即加入当前热词。

用户点击「加入热词」后：

1. 读取当前热词列表；
2. 按大小写不敏感规则去重；
3. 仅追加用户确认的候选；
4. 若来源是候选，则保存候选状态为 `added`；若来源是手动选择，则保存来源记录和选区；
5. 提示该词是否会进入下一次 ASR 请求。

当前 ASR 请求使用保守的 80-token 客户端预算，而内置词表远大于该预算。若新增候选仍排在大量默认词之后，可能不会真正发送给服务端。实现候选功能时，应优先发送用户确认的自定义热词，再使用剩余预算选择内置词；同时保留用户当前的词表内容和主动清空状态。

## 提取方式

手动选择路径不经过 AI，只使用本地字素簇拆分、选区合并、去重和校验。

自动提取路径推荐使用「本地初筛 + AI 排序」：

1. 本地排除空白、纯标点、常见虚词、过长文本和已有热词；
2. 本地统计重复次数，并识别英文、缩写、版本号和中英混合形式；
3. 在用户点击「整理当日内容」后，复用已经授权发送的当日原始记录，让 AI 补充专有名词候选与简短理由；
4. 严格解析结构化候选；解析失败时只保存整理正文，不生成候选。

候选提取应使用独立的数据契约，避免改变现有每日整理正文的纯文本结构。模型返回的候选仍需经过长度、字符、重复和敏感内容校验。

## 验收标准

- 每日整理正文和原始输入记录的现有行为不变。
- 不配置 AI 时，用户仍能从任意每日原始记录逐字选择并加入热词。
- 中文、英文、数字、emoji 和组合字符不会因 UTF-16 拆分而损坏。
- 相邻选区合并为一个热词；不相邻选区不会跨空白错误拼接。
- 取消选择或退出选择状态不会修改原始记录或热词列表。
- 候选不会自动加入热词。
- 已有热词、已忽略候选和大小写变体不会重复出现。
- 用户确认的新热词在预算允许时优先进入下一次 ASR 请求。
- 用户主动清空的热词不会因候选功能而恢复为内置默认词表。
- 敏感输入框不保存输入、编辑事件或候选。
- 宿主 App 或其他键盘完成的修改不会被宣称为 InkTalk 已观测的纠错。
- 只有验证成功的删除事件才参与纠错配对；长按删除按批次记录。
- 手动选择、自动候选和可能纠错在界面中显示不同来源标签。
- AI 候选解析失败不会影响每日整理结果保存。

## 建议实施顺序

1. 建立手动选择来源、候选热词和编辑事件数据表，并完成数据库迁移测试。
2. 实现每日记录逐字展开、连续／非连续选择、预览和批量加入热词。
3. 调整 ASR 热词优先级：用户确认热词优先，剩余预算再用于内置词。
4. 在热词管理页增加「待确认候选」入口，并保留用户自定义和主动清空状态。
5. 在删除键、长按删除、语音定稿、手写提交和数字键盘提交链路中记录可验证编辑事件。
6. 实现删除与新输入配对、局部差异提取和误判过滤，并在每日记录中展示可能纠错。
7. 增加每日自动候选提取和 AI 排序；解析失败时保留本地降级路径。
8. 使用多种宿主编辑器进行真实设备验收，再决定是否启用低置信度宿主文本监控。
